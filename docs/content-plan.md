# 「英语世界」内容收集方案

> 版本 v1.1 · 2026-10-07
> 定位：**候选来源与生产流程审查版**。每次正式发布前必须锁定具体版本/commit、保存 LICENSE 快照，并完成逐条内容审校；本方案不构成法律意见，也不把“开源代码许可”自动等同于“数据/生成服务内容许可”。

---

## 一、内容需求盘点（游戏内容模型）

一个场景 = 一份内容包，字段全部来自现有 demo 的 data.js 结构：

```
场景 Scene
├── 物品 Item（12~15 个）：en / zh / 音标 / emoji 图标
├── 词条 Word：单词 + 音标 + 中文 + 例句（en + zh 释义）
├── 音频 Audio：单词音 / 例句音（mp3，预生成静态文件）
└── 小游戏文案 GameLines：点单/清单台词模板 5~8 条
```

按 20 个场景规划的内容量：

| 内容类型 | 单场景 | 20 场景合计 | 备注 |
|---|---|---|---|
| 场景 | 1 | 20 | 咖啡店/超市/机场/学校/医院/餐厅/公园… |
| 词条（含音标+中文） | 12~15 | ~240~300 | CEFR A1→B1 递进；需做跨场景去重 |
| 例句（英+中） | 12~15 | ~240~300 | 每词至少 1 句，场景相关；翻译须审校 |
| 音频 mp3 | ~24~30 | ~480~600 | 词音+例句音；大小取决于编码和语速，不能预先保证 20MB |
| 小游戏台词 | 5~8 | ~100~160 | 可用模型辅助起草，必须人工审校和相似度检查 |
| 内容审计记录 | 1 份/场景 | 20 份 | 来源、版本、许可证、审校人、发布日期 |

## 二、来源评估（已逐项核实）

### 1. 词表骨架（决定"教哪些词"）

| 来源 | 内容 | 许可 | 结论 |
|---|---|---|---|
| **CEFR-J Vocabulary Profile 1.5**（github: openlanguageprofiles/olp-en-cefrj） | A1~B2 的词汇 profile；仓库另含独立的 Octanove C1/C2 文件。具体词条数必须以锁定版本的 CSV 实际统计为准。原始 CEFR-J 资料包含主题域信息，但需读取 CSV 列并逐项核对 | **CEFR-J 词汇/语法数据可用于研究和商业用途且不收费，但需正确引用**；Octanove C1/C2 是 CC BY-SA 4.0，不能混写 | ⭐ **首选骨架**。按主题域筛词前，先做字段和数量审计 |
| NGSL（newgeneralservicelist.org） | 高频通用词表；具体版本和数量需锁定 | 常见版本为 CC BY-SA 4.0，必须以原始版本声明为准 | 仅作为覆盖/频率补充；先评估 ShareAlike 对衍生词表和发布方式的影响 |
| Oxford 3000/5000 | 官方词表 | 不作为可直接抓取、复制和分发的开源数据源 | ❌ 排除，除非获得正式授权 |

**关键优势（待数据审计确认）**：CEFR-J 原始资料的主题域信息与“场景化游戏”天然匹配，但不能只依赖仓库 README 判断。第一步必须下载并检查 CSV 的列名、空值、重复项、主题域枚举和等级分布；如果某些词没有主题域，改用人工场景标签，并保留 `tag_source`。

### 2. 词条富化（音标/中文/词性/词频）

| 来源 | 内容 | 许可 | 结论 |
|---|---|---|---|
| **ECDICT**（github: skywind3000/ECDICT） | 官方 README 说明默认 `ecdict.csv` 是约 **76 万词条基础版**；仓库还提供其他压缩/分发形式。字段含音标、中文/英文释义、词性、词频、考试标签、词形变化等 | 仓库代码和数据的许可证/第三方来源必须分开审查；不能仅凭“GitHub 仓库可见”推断所有聚合字段均受同一 MIT 授权 | ⭐ **富化候选**。锁定 commit 后只抽取必要字段，并保留来源字段与版本记录；中文释义必须人工抽检 |

### 3. 例句

| 来源 | 内容 | 许可 | 结论 |
|---|---|---|---|
| **Tatoeba**（tatoeba.org） | 英语句子和翻译的持续更新语料；数量会变化，不能把一次搜索结果写成固定库存 | 默认文本许可为 **CC BY 2.0 FR**，但每条内容可能有不同作者/许可；音频许可独立，且可能有 NC/ND/SA 或不可外用限制 | 只在逐句保存 `sentence_id / author / license / source_url` 后使用；不要用单一总署名替代逐条归因 |
| AI 辅助生成例句 | 按场景、CEFR、已学词约束生成 | 不应笼统承诺“版权自有/独占”；不同模型、服务条款和司法辖区结论不同 | **主力起草方案**：生成后做人工语法审校、敏感内容筛查、与公开语料的相似度检查，并保留模型/提示词/日期记录 |

**推荐策略**：例句由模型辅助起草、人工定稿。Tatoeba 只做检索/语言参考，不把受不同许可约束的句子直接批量复制到产品；若实际采用 Tatoeba 句子，逐条保留作者、句子 ID、许可证和归因信息。

### 4. 音频

| 来源 | 内容 | 许可 | 结论 |
|---|---|---|---|
| **edge-tts**（github: rany2/edge-tts） | Python 模块/CLI，通过 Microsoft Edge 在线服务生成语音和字幕；支持多音色和 MP3 输出 | 仓库软件许可证与 Microsoft 在线语音服务条款是两件事；不能仅凭 GPL/LGPL 代码许可证明生成音频可商用 | 仅用于内部原型或在完成 Microsoft 条款审查后使用；预生成只解决运行时依赖，不解决服务授权问题 |
| Web Speech API（浏览器内置） | demo 现用方案 | 浏览器/系统能力，音频不落盘 | 仅作原型和无障碍兜底；音色随设备、离线能力和浏览器变化 |
| **正式方案（推荐）** | Azure AI Speech 官方 TTS，或其他明确允许产品分发的商业 TTS 服务 | 以服务条款、定价和输出内容条款为准 | 量产前锁定供应商，保存条款版本、voice、region、生成日期和成本记录 |

**风险对策**：原型阶段可以预生成并落盘，避免运行时受网络波动影响；但“落盘”不等于获得输出内容的商业分发权。正式上线前必须使用服务条款明确允许产品分发的供应商，并保存生成日志（文本 hash、voice、region、时间、服务版本/条款快照）。

### 5. 图标（物品视觉）

| 来源 | 风格 | 许可 | 结论 |
|---|---|---|---|
| **Fluent Emoji**（github: microsoft/fluentui-emoji） | Microsoft 风格，含 3D/扁平等资源 | 需以仓库当前 LICENSE 和资源目录声明为准；不能只凭项目名写成“MIT、无需署名” | 候选首选，但在下载脚本中保存具体 LICENSE 文件和 commit |
| Noto Emoji（github: googlefonts/noto-emoji） | Google 风格 | Apache 2.0（仍需保留 NOTICE/LICENSE 要求） | 备选，许可边界相对清晰 |
| Twemoji | Twitter 风格 | CC-BY 4.0（需署名） | 备选；保留 attribution |
| OpenMoji | 手绘风 | CC BY-SA 4.0 | 不作为首选；若使用必须接受署名和 ShareAlike 义务，不能简单称为“排除商用” |
| 系统字体 emoji（demo 现用） | 随平台漂移 | 依赖操作系统字体许可 | 仅 demo 过渡用，正式版必须自托管且锁定资源许可 |

## 三、推荐内容组合（一句话版）

> **骨架候选用 CEFR-J（先审计 CSV）→ 富化候选用锁定版本的 ECDICT → 例句由模型辅助起草并人工定稿 → 原型音频可预生成，正式版切换到条款明确的 TTS → 图标从已核实许可证的资源集中选择并自托管。**

这是一套低成本起步方案，不应宣传为“全程零成本、全部自动合规”。正式上线前需要承担 TTS、人工审校、许可证核验和内容维护成本。

## 四、加工 Pipeline（可脚本化）

```
scripts/content-pipeline/
├── 00_ingest_sources.py  # 下载固定 commit/tag + LICENSE/README 快照 + SHA256
├── 01_audit_profiles.py  # 统计 CSV 行数、列名、空值、重复、等级和主题域分布
├── 02_select_words.py    # 场景+等级+学习目标 → 候选词；跨场景去重并人工确认
├── 03_enrich.py          # 查锁定版本 ECDICT → 音标/中文/词性/词频；记录 source_id
├── 04_gen_sentences.py   # 模型辅助起草 → 人工定稿/相似度/安全筛查 → sentences.json
├── 05_gen_audio.py       # 仅调用已审查条款的 TTS → audio + 生成日志/文本 hash
├── 06_gen_icons.py       # 拉取已核实许可证的 SVG → LICENSE/来源映射
├── 07_review_scene.py    # 内容、发音、图标、难度、版权逐项验收
└── 08_build_scene.py     # 汇总产出 scenes/{scene}.json（与 data.js 同构）
```

- 每个脚本独立可重跑，失败断点续跑
- 产出 JSON 直接被现有 demo 的数据结构消费
- 产能不要先拍脑袋承诺：首个场景做“基准场”，记录下载、去重、生成、试听、审校和返工耗时；至少完成 2~3 个场景后再估算平均产能。原型期可按 **每场景 0.5~1.5 个工作日** 规划，批量化后再压缩。

## 五、内容数据模型与验收边界

现有 `data.js` 适合 demo，但量产必须升级为可追溯模型。每条内容至少包含：

```json
{
  "id": "cafe.coffee",
  "headword": "coffee",
  "forms": ["coffee", "coffees"],
  "pos": ["noun"],
  "cefr": "A1",
  "topic": "Food and drink",
  "scene_id": "cafe",
  "meaning_zh": "咖啡",
  "ipa_us": "...",
  "ipa_uk": "...",
  "source": {"dataset": "ECDICT", "version": "commit-sha", "field": "phonetic"},
  "license": {"name": "...", "url": "..."},
  "sentence": {
    "en": "...", "zh": "...", "origin": "original|tatoeba|edited",
    "source_id": "...", "author": "...", "license": "..."
  },
  "audio": {"url": "...", "voice": "...", "generated_at": "...", "text_sha256": "..."},
  "asset_review": {"content": "pending|approved", "audio": "pending|approved", "icon": "pending|approved"}
}
```

**必须新增的内容控制：**

- `sense_id`：同形异义词拆 sense，不能只按 headword 合并。
- `POS` 和词形：例句中的词性/变形要与教学目标一致。
- `prerequisite_ids`：场景之间的输入依赖，避免 A1 场景突然出现未教的 B1 词。
- `known_word_policy`：定义“已学词”是全局已学、场景已学还是允许少量新词。
- `safety_flags`：敏感、医疗、法律、金融、文化争议内容必须进入人工复核队列。
- `source snapshot`：保存原始文件、commit/tag、下载时间、SHA256 和许可证快照。

**场景上线门槛：**

1. 词表和等级字段 100% 可追溯；
2. 每个词至少 1 个已审校例句和可播放音频；
3. 例句中的目标词、词形、词性与卡片一致；
4. 自动检查未学词比例，人工确认所有高风险句；
5. 每个第三方资产都有来源、作者、许可证和 attribution；
6. 产品内有“内容来源与许可”页面，并能定位到版本/commit。

## 七、质量标准（每个场景上线前 checklist）

- [ ] 12~15 词，全部属于该场景主题域，等级偏差 ≤1 级
- [ ] 音标来自 ECDICT（真实数据），非 AI 编造
- [ ] 例句长度 ≤10 词、只含已学+本场景词（可理解输入原则）
- [ ] 例句逐条人工抽检语法（AI 生成必须过人眼）
- [ ] 每个词有 mp3（试听确认发音正确）与 SVG 图标（视觉确认语义匹配）
- [ ] 小游戏台词 5~8 条，句式有变化
- [ ] 无版权风险：图标来自 Fluent Emoji、例句 AI 自有、词表已引用出处

## 九、版权合规清单（站内署名页必备）

1. **CEFR-J**：引用 "The CEFR-J Wordlist Version 1.5, Compiled by Yukio Tono, Tokyo University of Foreign Studies"，并保存实际下载版本/日期；CEFR-J 词汇与语法数据的商业使用条件以其 Terms of Use 为准。
2. **Octanove C1/C2（若采用）**：单独按 CC BY-SA 4.0 履行署名和 ShareAlike 义务，不要与 CEFR-J 的许可混写。
3. **ECDICT**：锁定具体 commit；仓库 README 说明 `ecdict.csv` 默认约 76 万词条基础版。保留仓库 LICENSE、数据文件来源说明和第三方来源记录，不直接把所有聚合数据宣称为 MIT。
4. **Tatoeba（若实际使用文本）**：逐句保存 sentence ID、作者、许可证、来源 URL，并按句子许可证归因；默认文本 CC BY 2.0 FR 不代表所有音频或所有句子都同一许可。
5. **图标**：每次下载保存具体仓库 commit、资源路径、LICENSE/NOTICE 和 attribution；Fluent Emoji 的最终许可必须以所下载版本仓库文件为准。
6. **TTS 音频**：保存供应商、服务条款版本、voice、region、生成日期和文本 hash；不能用“预生成”替代商业分发权审查。
7. **AI 辅助内容**：保存模型、版本、提示词、生成日期、人工编辑记录和相似度检查结果；不要在没有法务依据时承诺模型输出为独占版权。

## 十、审查结论与分阶段执行

原 v1.0 方向正确，但不能直接按“全量自动生产、全部可商用、4 周 20 场景”执行。建议分三阶段：

### 阶段 0：2~3 天，做数据与许可基线

- 锁定 CEFR-J、ECDICT、图标仓库的 commit/tag，下载原始文件和许可证快照。
- 对 CEFR-J CSV 做字段/数量/主题域/等级统计，对 ECDICT 做字段和覆盖率统计。
- 建立 `content_provenance.csv`，每个词、句子、音频、图标都有来源和审校状态。

### 阶段 1：1~2 周，重制两个基准场景

- 只做咖啡店和超市，各 12~15 词。
- 跑通去重、选词、词条富化、例句审校、TTS、图标、构建和站内归因页。
- 记录每个环节耗时、返工率、音频失败率、未学词比例。

### 阶段 2：再决定批量扩展

- 若两个场景的内容验收指标稳定，再扩展到家、学校、公园、餐厅等 4~6 个 A1/A2 场景。
- 20 场景是内容路线图，不是第一版承诺；应根据真实复用率、重复词率和用户反馈调整。

### 本次审查的关键修正

- CEFR-J 的字段/数量/主题域必须按锁定 CSV 实测；不能仅凭 README 写死 7,570。
- ECDICT 默认 `ecdict.csv` 是约 76 万词条基础版；“340 万”不能作为当前默认数据规模。
- 数据、代码、TTS 服务、AI 生成内容、图标资产分别建许可档案。
- Tatoeba 逐句归因；AI 输出只视为候选草稿，不笼统承诺为独占版权。
- 预生成音频只能解决运行时依赖，不能替代 TTS 服务条款审查。
- 4 周 20 场景的产能估计过于乐观，先用基准场景实测。
